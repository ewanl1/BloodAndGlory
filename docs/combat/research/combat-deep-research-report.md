# Technical report on a testable melee combat system for Blood and Glory

## Context and design goals

For **Blood and Glory**, the most robust approach is a **hybrid combat architecture**: keep gameplay rules in a small, deterministic, plain-C# combat core, and let Unity-specific components act as adapters for input, physics queries, animation, audio, and VFX. That recommendation is strongly supported by three separate lines of evidence: Unity’s test assemblies are explicitly designed to keep tests separate from shipped code; ScriptableObjects are intended to hold shared data cleanly; and OpenAI’s Codex guidance says agents work best with clear repository instructions, explicit validation steps, and well-scoped tasks. In VR specifically, close-range sword interactions are harder than standard game combat because the player’s motion is natural, fast, and partly unpredictable; research on interactive VR sword fighting has shown value in separating low-level physical interaction from a higher-level semantic behaviour layer. citeturn18view0turn18view12turn24view5turn24view2turn24view6turn26view0turn27view0

My overall confidence is **high** for the Unity-specific engineering recommendations in this report, because they are grounded mostly in Unity’s official manuals and APIs. Confidence is **medium** on exact “feel” tuning for Blood and Glory specifically, because VR melee feel depends heavily on headset latency, controller sampling, target platform, weapon length, enemy animation style, and whether you want realism or a deliberately “gamey” response. That uncertainty does not change the architecture recommendation; it mainly affects tuning values and content authoring workflows. citeturn17view15turn19view4turn19view5turn18view7

The core design objective should therefore be: **every important combat rule must be expressible and testable without running a whole arena scene**. Unity scenes, prefabs, NavMesh, and animation clips should be treated as data and adapters around that core, not as the place where the real combat truth lives. That is the safest design for incremental implementation and for AI coding agents, because it minimises hidden state, race conditions, and accidental regressions. citeturn18view0turn18view5turn24view2turn24view4turn24view8

## Recommended architecture

I recommend organising the combat code into **five assemblies** and making that layout explicit in the repository instructions for Codex:

```text
Assets/BloodAndGlory/
  Combat/
    Core/          // pure C# domain rules
    Runtime/       // MonoBehaviours, adapters, presenters
    Editor/        // validators, import checks, tooling
    Tests.EditMode/
    Tests.PlayMode/
  AI/
  Characters/
  Arena/
AGENTS.md
```

This matches Unity’s assembly/test-assembly model and gives Codex an obvious boundary for small, reviewable changes. In `AGENTS.md`, define the allowed directories per task, the commands to run Edit Mode and Play Mode tests, the coverage command, and the exact “done when” conditions for each subsystem. OpenAI’s Codex guidance is very explicit that `AGENTS.md`, build/test commands, and well-scoped tasks materially improve reliability. citeturn18view0turn18view1turn24view5turn24view2turn24view8turn24view9

Inside `Combat.Core`, use **plain data objects** such as `AttackDefinition`, `HitProposal`, `DamageContext`, `BlockContext`, `CombatState`, and `CombatEvent`. Store enemy/weapon tuning in ScriptableObjects, but do not put the actual decision logic inside those assets; use them as data containers that the pure C# services consume. Unity’s own guidance describes ScriptableObjects primarily as shared data stores, which is exactly what you want for agent-safe combat tuning. citeturn18view12turn18view0turn18view5

For **hit detection**, do **not** let `OnCollisionEnter` or `OnTriggerEnter` be the sole authority for damage. Unity’s CCD documentation says CCD is a safety net, not a guarantee of physically exact results; sweep-based CCD is aimed at fast linear collisions, while Continuous Speculative handles angular motion better but can still produce missed collisions or false collisions. That matters a lot in VR, where swords and clubs often rotate quickly around the hand between fixed steps. The safest pattern is to run your own physics queries in `FixedUpdate` against the relevant `PhysicsScene`, and treat collision callbacks as secondary signals for effects and contact feel, not as the source of truth for damage. citeturn34view0turn17view0turn17view1turn34view1turn19view6turn17view6

For **weapon sweep detection**, the most implementable and testable option is a **sample-point sweep** rather than a single collider event. Cache the previous fixed-step world positions of several weapon markers, such as guard, lower blade, upper blade, and tip. On the next fixed step, spherecast each marker from previous to current position, then run an `OverlapCapsuleNonAlloc` or `PhysicsScene.OverlapCapsule` over the final weapon segment(s) to catch start-overlaps and slow-contact cases. Unity’s query APIs support layer masks and explicit trigger handling, and Unity notes that SphereCast and CapsuleCast do not detect colliders already overlapped at the start of the sweep, which is why the follow-up overlap pass is important. Use non-allocating query variants to avoid managed heap churn during frequent melee checks. citeturn35view0turn33view0turn33view1turn28view0turn28view1turn19view0turn18view9

For **hitboxes and hurtboxes**, use **primitive child colliders** grouped into **compound colliders** on characters, not animated MeshColliders. Unity’s documentation says primitive colliders are the most computationally efficient, and compound colliders are generally preferable to a complex dynamic MeshCollider for moving bodies. For Blood and Glory, that maps cleanly to region-based hurtboxes such as head, torso, arms, and legs. Add a small `HurtboxAuthoring` component to each collider that exposes a region enum, damage multiplier, and team ownership. Put hurtboxes on dedicated layers so combat queries can filter them without touching scenery, weapons, or helper triggers. citeturn17view19turn17view18turn19view3turn19view1turn19view2turn18view9

For **health and damage resolution**, use a one-way pipeline: `HitDetection -> HitProposal -> CombatResolver -> HealthService -> CombatEvents`. The resolver should be the only place that decides whether a proposal becomes damage. Its responsibility should include duplicate-hit suppression, friendly-fire filtering, attack-window validation, block/parry handling, armour or region multipliers, stagger, death, and event emission. This is a recommendation rather than a Unity API rule, but it follows directly from Unity’s testing model and the Codex guidance to keep work scoped and validation-driven: the more of the combat system you can keep inside a pure resolver, the more of it you can prove in Edit Mode tests before touching scenes or animations. citeturn18view0turn18view5turn24view2turn24view4

For **blocking and parrying**, treat them as **stateful resolution rules**, not as incidental physics behaviour. A block should mean “the defender has an active block state and the incoming attack intersects the relevant block volume or weapon lane”. A parry should mean the same thing plus a tighter timing requirement and a different outcome, such as stagger or attack interruption. That structure lets you unit-test every edge case: block succeeds but no damage; parry succeeds and interrupts; block fails because the volume was wrong; block fails because the timing window ended. Leave sparks, sounds, and haptic feedback to presentation listeners on `CombatEvent`s. citeturn17view16turn19view9turn19view10turn18view5

For **NPC AI and behaviour**, use a small **code-side gameplay state machine** for decision-making and let the Animator remain mostly presentational. Unity’s AI Navigation docs give the key constraints: `NavMeshAgent` exposes speed, acceleration, angular speed, and stopping distance for controllable movement; mixing a non-kinematic Rigidbody with a NavMeshAgent creates a race condition; and root-motion animation can also fight with NavMesh unless information flows in one direction only. For an arena game, a simple state set is enough: `Spawn`, `Approach`, `Strafe`, `Telegraph`, `AttackCommit`, `Recover`, `Block`, `Stagger`, `Dead`. The AI chooses attacks and windows in code; the Animator displays them. citeturn17view13turn23view4turn23view5turn19view12

For **animation-driven enemy attacks**, author each attack as data. A practical pattern is an `AttackDefinition` ScriptableObject containing the clip, telegraph period, active strike window, recovery period, optional root-motion mode, damage profile, and allowed follow-ups. Then use either animation events or a tiny state hook to notify the runtime when those authored windows start and end. Unity supports Animation Events directly, exit times on transitions, root-motion control, and state callbacks such as `OnStateEnter`, `OnStateUpdate`, and `OnStateExit`; but none of those should own the game rule itself. They should only synchronise the authored animation with the combat core. citeturn17view16turn19view8turn19view10turn21view0turn21view1turn18view12

Use **StateMachineBehaviours sparingly**. Unity notes that certain Animator callbacks disable multithreaded state-machine evaluation, and the Profiler documentation says Animator cost scales with the complexity of states, transitions, properties, and layers. That is a strong reason to keep combat state in code and keep the Animator graph small, clean, and content-facing. Use sub-state machines to keep presentation graphs understandable, but let the gameplay FSM decide when the NPC is actually telegraphing, committed, staggered, or dead. citeturn17view17turn30view0turn31view0turn31view2

For **physics-based player weapons**, use a **hybrid visual/authoritative model**. XR Interaction Toolkit documents the trade-off well: `Instantaneous` movement minimises latency but can let colliders visually trail or pass through geometry, while `Velocity Tracking` and `Kinematic` movement update in `FixedUpdate` and improve collision accuracy at the cost of lag behind the hand. For Blood and Glory, the best compromise is usually: a visually responsive weapon that follows the VR hand closely, plus an authoritative combat proxy that is updated in fixed time and used for sweep detection. If you want stronger physical follow and self-stabilising motion, a `ConfigurableJoint` can constrain axes and add spring/damper behaviour, but the tuning burden is much higher and should come only after the query-driven combat loop is working. citeturn19view4turn19view5turn17view14turn19view6turn20view0turn20view1

For **prefab validation**, combine runtime-safe and editor-only safeguards. `RequireComponent` should enforce hard dependencies like a Rigidbody, Animator, or required authoring component. `Reset` should set sane defaults the first time a component is added. `OnValidate` should clamp or reject invalid serialized values. Then add an Editor validator that finds all combat prefabs with `AssetDatabase.FindAssets`, loads them into isolated scenes with `PrefabUtility.LoadPrefabContents`, and checks rules such as: required layers exist; hurtboxes have regions; attack definitions reference clips; attack windows are strictly ordered; NavMeshAgent/Rigidbody ownership rules are obeyed; and no prefab depends on missing child references. citeturn18view11turn9search3turn17view7turn17view8turn17view9

## Alternatives and trade-offs

A **collision-callback-only** system is the shortest path to a prototype, because you can put colliders on weapons and react to trigger/collision messages immediately. The downside is that VR melee exposes every weakness in that approach: fast angular motion, fixed-timestep gaps, duplicate contacts, and physics-order noise. Unity’s own documentation on CCD and trigger handling makes it clear that relying only on those callbacks is brittle for high-speed close-range weapons. A callback-only model is fine for sparks and controller rumble; it is a poor main damage authority. citeturn34view0turn17view1turn19view1turn19view2

A **fully physics-authoritative held weapon**—dynamic Rigidbody, strong contacts, and no custom sweep queries—can feel exciting and emergent, and Unity’s joint system is flexible enough to support it. The trade-off is stability, tuning time, and testability. You must manage latency, oscillation, self-collision, and movement ownership carefully, and you still need gameplay rules around duplicate hits, attack validity, and blocking. For a first implementation that Codex can change safely, this is the wrong default. It should be treated as a later enhancement, not the foundation. citeturn20view0turn20view1turn19view4turn19view5

For NPCs, you have a real choice between a **code FSM** and **Unity Behavior**. Unity Behavior now provides graph-based AI authoring, modular composition, subgraphs, and blackboards, which can be attractive for designers and for more elaborate encounter logic. The trade-off is that visual graphs are usually less diff-friendly, less straightforward for line-by-line code review, and less natural for agent-generated patches than a small code FSM with clear tests. For Blood and Glory, I would use code for the combat loop and reserve Unity Behavior, if at all, for higher-level encounter orchestration later. citeturn18view14turn18view15turn31view3

For enemy attacks, you can choose between **Animator-owned timing** and **data-owned timing**. Animator-only timing is fast to author, but it scatters truth across clip events, graph transitions, and controller state. Data-owned timing via `AttackDefinition` assets is a little more work up front, but it is far easier to validate and test. The most pragmatic compromise is to let animation events and Animator states signal transitions, while the real attack windows live in data assets consumed by the combat core. citeturn17view16turn19view8turn18view12

## Testing and automatic validation

The testing strategy should follow a **combat pyramid**. Most tests should be **Edit Mode** because Unity’s test assemblies let you test code without shipping those tests, and because plain-C# resolver logic is cheaper and more stable to verify there. Edit Mode should cover damage resolution, block/parry outcomes, duplicate-hit suppression, attack-window ordering, FSM transitions, and all prefab/asset validators. Structure those tests with clear Arrange-Act-Assert patterns so they double as executable documentation for future Codex tasks. citeturn17view4turn18view0turn18view5turn18view1

Use **Play Mode tests** for the places where Unity’s runtime matters: weapon query integration against colliders, attack window synchronisation with animation, NavMeshAgent–Animator ownership rules, scene bootstrap, and death behaviour in a real scene. Unity’s Test Framework supports Play Mode tests as coroutines and supports scene-based tests, which is exactly what you need for “spawn into arena, engage NPC, confirm minimal combat loop works” smoke tests. citeturn17view4turn18view6turn17view15turn23view4

For reliable combat tests, create **local physics scenes** and simulate them manually. Unity supports manual simulation through `Physics.Simulate` and `PhysicsScene.Simulate`, and only the objects in that scene are affected. That is valuable because you can build tiny deterministic combat fixtures: one sword proxy, one enemy hurtbox rig, one blocker, and a known fixed timestep. You can then reproduce tunnelling, overlap, and block cases without the noise of a full gameplay scene. citeturn17view5turn17view6turn13search17

Use **log assertions and validation failures as first-class tests**. Unity’s test framework treats unexpected errors and exceptions as test failures by default, and `LogAssert.Expect` lets you state which warnings or errors are intentional. That makes prefab validation especially powerful: if your validator logs “Enemy prefab missing Head hurtbox”, the test should fail immediately. This is exactly the kind of hard boundary AI coding agents benefit from, because it turns setup drift into an objective signal instead of a manual review task. citeturn18view4turn17view7turn17view8turn17view9

Run the whole suite in CI from the command line and collect coverage. Unity’s Test Framework supports `-runTests -batchmode`, and the Code Coverage package can emit coverage reports from automated runs. In practice, that means every Codex-issued combat change can be gated on: Edit Mode green, Play Mode green, prefab-validation green, and coverage not dropping under an agreed threshold for `Combat.Core`. citeturn18view2turn18view3turn24view4turn24view2

For agent safety specifically, follow OpenAI’s published workflow: keep tasks well-scoped, write prompts like small GitHub issues, ask the model to generate or update tests as a separate step, and verify that relevant tests fail before the feature implementation lands. This is one of the highest-value process controls you can add to Blood and Glory. citeturn24view8turn24view9turn24view4turn24view5

## Implementation roadmap

**Phase A — repository scaffold.** Create the assembly layout, add `AGENTS.md`, define the test commands, and add an empty `Combat.Core` with a trivial passing Edit Mode test. “Done when” means Codex can explain the repo instructions back to you, and CI can run at least one Edit Mode test from batch mode. citeturn24view5turn18view1turn18view2turn24view2

**Phase B — core combat domain.** Implement immutable combat inputs and outputs first: `HitProposal`, `DamageContext`, `CombatEvent`, `HealthState`, and a `CombatResolver`. Add Edit Mode tests for block/no-block, parry/no-parry, duplicate-hit suppression, friendly-fire filtering, damage multipliers, death transitions, and stagger. “Done when” means those rules are fully testable without GameObjects. citeturn18view0turn18view5turn24view4

**Phase C — hurtboxes and player weapon sweeps.** Add region hurtboxes to one enemy prefab, add a weapon sweep profile to one player weapon, and implement fixed-step sample-point sweeps plus overlap refinement. Add Play Mode tests proving that a fast swing still hits, a stationary overlap still hits, and the same victim is not damaged repeatedly by the same attack window. citeturn35view0turn33view0turn33view1turn28view0turn17view4

**Phase D — enemy locomotion and one authored attack.** Add a minimal NPC FSM using `NavMeshAgent`: approach, telegraph, commit, recover. Author one `AttackDefinition` asset and bind it to one animation clip. Add Play Mode tests for “enemy approaches player”, “telegraph occurs before active window”, and “agent/animation movement ownership does not conflict”. citeturn17view13turn23view4turn17view16turn21view0turn21view1

**Phase E — blocking, parrying, and death loop.** Add block state, parry state, interrupted attack state, stagger, and death. Add prefab validation checks that every combat-capable enemy includes required hurtboxes, references, layers, and state bindings. Add tests that validate transition outcomes from all combat states. citeturn17view7turn18view11turn17view8turn17view9turn19view10

**Phase F — arena smoke and regression suite.** Build a smallest-possible arena scene with one spawn point, one enemy, and a lightweight combat HUD/debug overlay. Add scene-based Play Mode tests for spawn, first engage, first hit taken, first enemy death, and respawn or reset. Add code coverage reporting and make this vertical slice the baseline that every future Codex combat task must preserve. citeturn18view6turn18view3turn24view2turn24view4

## Risks

The biggest technical risk is **missed or false hits**. Unity’s documentation is clear that CCD is not perfect, that speculative CCD can create ghost contacts, and that larger fixed timesteps reduce CPU cost but increase jitter and tunnelling risk. The mitigation is the hybrid model recommended above: fixed-step custom sweep queries, overlap refinement, nonalloc buffers, and Play Mode regression tests for fast swings and edge overlaps. citeturn34view0turn34view1turn18view7turn28view0

The second major risk is **movement race conditions** between NavMesh, Rigidbody physics, and root-motion animation. Unity’s AI Navigation guidance explicitly warns about race conditions when NavMeshAgent competes with a non-kinematic Rigidbody, and also warns that NavMeshAgent with root-motion animation can create hard-to-debug feedback loops unless information flows one way. The mitigation is simple but non-negotiable: at any moment, exactly one subsystem owns movement. citeturn23view4turn23view5turn17view15turn21view0

The third risk is **content drift across prefabs and animations**. Arena combat projects often become fragile because some enemy prefabs have extra hurtboxes, some clips have events, and some controller states bypass the intended rules. The mitigation is to move combat timing into named data assets, add prefab validators, and make those validators part of Edit Mode CI, not an optional menu item. citeturn17view7turn17view8turn17view9turn18view4

The fourth risk is **performance and debugging complexity**. Animator cost rises with state-machine complexity; some state-machine callbacks constrain evaluation; trigger processing shows up explicitly in Unity’s profiler; and fully physical held weapons can become a tuning burden. The mitigation is disciplined scope: keep the Animator lean, keep combat rules in code, prefer explicit queries over sprawling trigger networks, and introduce joint-driven physical weapon follow only after the deterministic combat slice is stable. citeturn30view0turn17view17turn19view4turn20view0

## Open questions and limitations

A few project-specific choices will materially affect tuning, even though they do not change the recommended architecture. The first is whether Blood and Glory targets **PC VR only, Quest-class standalone, or both**; that changes physics budget and fixed-timestep tolerance. The second is whether enemy attacks should use **full root-motion commits** or mainly **in-place attacks with scripted displacement**; both are viable, but the ownership rules need to be decided early. The third is whether the player weapon should prioritise **strict physical resistance** or **responsive “hero weapon” handling**; the correct balance changes how much joint-based follow you add after the core query system is working.

This report also intentionally favours **determinism and agent-safe implementation** over the most advanced possible VR combat behaviours. Research systems such as data-driven reactive sword fighters are promising, but they are a second-generation step. For Blood and Glory, the correct first milestone is a deterministic, continuously validated melee loop that can be expanded safely. citeturn26view0turn27view1
